# G0 实机核验指南

目标是验证真实数据，不以演示或单元测试替代驾驶实验。

## 准备

1. 记录 ACC 安装版本，启动一次单人练习，选择已知车型与赛道。
2. 启动 `Start-DeltaTR.cmd`，确认是 ACC 实时模式，而不是 SYNTHETIC 或 FILE REPLAY。
3. 先静止检查 车名、赛道、游戏版本、速度、气温和路温。所有未校准字段应为 NeedsVerification。
4. 开始 JSONL 录制。也可执行 `scripts/probe.ps1 --duration 1800 --record recordings/g0.jsonl`。

## 场景

| 场景 | 应验证 |
|---|---|
| 静止、加速、换挡 | 速度、挡位编码、转速、四轮顺序 |
| 冷胎到热胎 | 胎压/核心温度是否与 HUD 语义一致 |
| 空气/路温变化 | 度数、刷新频率和值域 |
| 整圈与跨起终线 | 圈数、上一圈时间、排名 |
| 进站加油 | fuel 原始值是否等于升或千克，不靠旧文档猜单位 |
| 暂停与游戏重播 | 禁止实时查询数值 |
| 退出赛道、换车、换图、重开比赛 | 旧状态失效，合理产生新会话 |
| 强制退出和重新启动 ACC | 不崩溃，重新打开映射，旧句柄不继续当新赛况 |
| 调整天气 | 当前雨势、预报类别、抓地等级，而非精确降雨时间 |

## 使用校准向导（推荐）

1. 在真实 ACC 驾驶模式进入左侧“数据校准”，点击“打开校准向导”，然后点击“冻结当前遥测”。演示、历史文件回放、已停止、暂停和过期数据不会通过。
2. 记下冻结时刻对应的 HUD 值，选择字段，填入数值、已确认的单位和场景备注。不要将之后变化的 HUD 读数与旧冻结帧比较。
3. 点击“加入人工对照”。原始数值与 HUD 值超过字段默认容差时直接拒绝；重复来源时间戳也拒绝。当前容差是软件比较阈值，不是实机精度结论。
4. 在另一时刻再次冻结，重复该字段的对照。推荐包含静止/行驶、冷胎/热胎等不同场景。**两个样本只是导出下限，不代表研究验收充分。**
5. 填写实验说明，点击“保存校准包并加载”。只授权至少有两条合格证据的字段；其余字段继续保持待核验。

向导目前覆盖速度、燃油、气温、路温、排名、圈数、上一圈时间、前车差距和四轮压力/核心温度，共 16 个字段。圈速和差距按毫秒填写（如 1.84 秒输入 1840），不会自动单位换算。

冻结之后原始样本保持不变，填表无需持续追赶遥测刷新；若车辆、赛道或版本改变，应关闭并重新打开向导创建新草稿。关闭窗口会放弃未保存草稿。

导出的两个文件：`<name>.json` 为校准配置，`<name>.<id>.evidence.json` 为逐项对照证据。后者包含原始值、HUD 值、单位、容差、来源、观测时间、冻结时间、会话和备注。配置使用同目录相对文件名及 SHA256 校验；证据缺失或内容变化时拒绝加载。必须将两个文件一起移动。

SHA256 用于检测意外文件不一致，不认证人工观察是否真实，也不是不可伪造的签名。请保留 HUD 记录或截图供人工核查。

## 手工写入校准记录（兼容旧版）

复制 `config/calibration.example.json` 为 `config/my-car.local.json`。先在独立文件写 HUD 对照证据，再填入精确上下文。

下面只说明格式，**不得把示例当作已通过验证的配置**：

```json
{
  "gameVersion": "填写探针显示的真实版本",
  "sharedMemoryVersion": "填写探针显示的真实版本",
  "carModel": "填写精确车型标识",
  "track": "填写精确赛道标识",
  "evidence": "填写本次人工 HUD 比对记录的本地路径与日期",
  "verifiedUnits": {
    "airTemperature": "°C",
    "roadTemperature": "°C"
  }
}
```

逐项验证后逐项加入。四个胎压键为 `pressure.FL / pressure.FR / pressure.RL / pressure.RR`，单位 `psi`；核心温度键为 `temperature.FL / ...`，单位 `°C`。燃油仅在核实后写 `"fuel": "L"` 或 `"fuel": "kg"`，不会进行隐式质量/体积转换。

版本、车型或赛道不一致时整个 profile 不授权；新增字段不因其他字段已验证而自动授权。手工配置没有 `evidenceSha256` 时，`evidence` 仍是追溯引用；软件不会自动判断一份人工证据是否真实充分。

## 录制质量报告

结束录制后进入左侧“录制与回放”，点击“查看质量报告”，选择 JSONL 文件，可查看统计并保存 JSON。命令行等效操作：

```powershell
./scripts/probe.ps1 --replay recordings/g0.jsonl --analyze --report artifacts/g0-quality.json
```

- 真实 Live 帧与合成帧分开计数；暂停/重播/断开单独列入 phases。
- 字段新鲜解码比例的分母为全部真实 Live 帧；缺失也计入分母。16 个核心字段即使整段缺失也列出。
- 新鲜解码包含 NeedsVerification 和 Estimated；只有 Valid 且未过期、非估计的字段计入“已校准新鲜帧”。
- “可覆盖的真实驾驶区间”只累计相邻帧都是同一真实 Live 会话且间隔不超过 2 秒的区间；长空洞不计为连续驾驶。
- spanSeconds 是首末记录间距，recordedFramesPerSecond 是录制帧率；均不等于游戏更新率、采样线程性能或已完成的 30 分钟验收。
- 报告读取全部记录，坏行和空文件会报错；不会静默跳过。报告和校准文件均禁止覆盖已有文件。
- G0 始终留给人工验收，不依据报告自动通过。

## 验收与限制

至少验证 10 个高优先级字段，并连续驾驶 20–30 分钟，检查录制丢帧、异常质量、游戏性能影响。将结果填写到字段矩阵及验证报告。

当前没有 SDK 自动检测器、录像比对器或 CPU/帧时间统计器；这些数值需实测记录。没有实时 ACC 时不能宣告 G0 通过。G0 通过之后再进入麦克风、方向盘按键和语音模型开发。
